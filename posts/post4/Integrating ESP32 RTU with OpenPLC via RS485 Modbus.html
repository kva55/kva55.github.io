Integrating ESP32 RTU with OpenPLC via RS485 Modbus

About Blog Contact

Building an ESP32 RTU and using modbus to communicate with OpenPLC.

This project started with a simple question: "How can my PLC receive temperature data from my DHT11 sensor?". For anyone that ever dealt with an introductory robotics course, or tinkered around with an arduino will know it's quite easy to setup.

The DHT11 Sensor by itself has 4 connections, though, only 3 are used. These are the data, ground, and 3.3v pins. Hook that up to an arduino, initialize the pins, paste some simple code within the loop and viola, you can get a low-accuracy temperature and humidity data.



That was not that case for connecting to a PLC, and the reason might be surprising. That is because the DHT11 actually uses a single-wire 2-way proprietary protocol. In otherwords, while there are arduino libraries that can specifically interface with sensors using that protocol to read and write data, such as with the adafruit DHT sensor library, that information still needs to be understood and or processed by something that does not support it.

In industrial controls, there's a type technology called an RTU (Remote Terminal Unit). While the actual definition can mean many different things, I will focus on this: an RTU can convert signals or data from one form into another. This allows for one process to understand what a proprietary data represents, and can have controls process and compute it.

At this point, an RTU can be a lot of things, but with two caveats:

  1. Data Acquisition: It has to collect the signals/data that are required (so communicate via the protocol the sensor operates on)
  2. Upstream Communication: It has to communicate to the controller, or PLC in this case.


The OpenPLC can function on modbus, and for this project that is what I used. Modbus is a serial protocol when used for a PLC, with some different standards that span the OSI model.
      Serial-Based: RS485 is a electrical signaling specification. By itself, it is not a protocol, which is where modbus rolls in. By using modbus over electrical signaling, we can actually perform serial communication over pure copper. (Okay, it sounded cooler in my head before I wrote it.)
      TCP-Based: Modbus TCP (Ethernet) on the otherhand does not operate over lines, but is encapsuated inside the ethernet frames and network packets. This is the typical port 502 communication between PLCs.

For this project, I decided I wanted a challenge and pursued RS485 communication. Before I document what components I purchased, serial-based modbus has transmission modes. While this isn't exactly groundbreaking, understanding this from the get-go will save some troubleshooting headaches.
  • Modbus RTU: Data is sent in binary or hexadecimal formats. It is possible to transmit complex data like 32-bit floats. (Unless you really know what you're doing, I suggest sticking to simpler data types, or you'll have fun with OpenPLC).
  • Modbus ASCII: Human-readable data.

Modbus Architecture

Architecturally, modbus follows a client/master communication, regardless of what standard or transmission mode that is used. The master device begins all communication, to which the client (or slave) can respond. The client does not start communications first, unless of course we force it!

Testing by Breaking Standardization

The reason I mention about forcing non-standard communication is because I did so to verify my MAX485 was communicating and connected properly to the RS485-To-USB adapter. By sending signals directly from the client device through the USB adapter, you will actually see the "RX" LED flash, and when receiving communication from the master, the "TX" LED.

note: I think it is possible to have MAX485-to-MAX485 communication completely bypassing the USB requirement; however, due to the time constraints the USB was used.

Physical Addressing References

When working with OpenPLC, mapping any physical connections to registers or "coils" needs to be done via GPIO pins. Much like an RTU translates signals from one format into another, the same needs to be done between physical GPIO pins, and what OpenPLC recognizes inputs and outputs based on the IEC 61131-3 Memory Addressing. Raspberry pi physical addressing specifically for the OpenPLC project can be found here, but other microcontrollers and computer addresses can be used similarly.

The above image shows the standard voltage divider formular. On paper, the formula would give a perfect 3.33v output. In reality, this can fluctuate and change, and if underpowered can actually cause modbus data to never transmit if the signal doesn't pass the HIGH threshold.

I ended up taking a small deep dive into voltage dividers, since this kind of interested me for the project. Because of how division works, you can change the resistors R1 and R2 with different base-tens, and always end up with 3.33v as the output, but the actual current will be different. As a quick example, with a 30kohm voltage divider, the speed at which the signal can reach the ESP32 is significantly slower than a 3kohm (kind of literally, as there's less resistence for the signal to pass through).

The First Modbus Request with an ESP32 RTU

Lets look at the ModbusRTUSlave library. This library worked for my purposes, and it turned out to be finnicky to work with master-based libraries. It could have been a compatibility issue too, but luckily this library had support for the ESP32.
  • First, you have the modbus.poll() in the loop, with the slave ID of 1.
  • Next, you assign local registers as holdingRegisters[2], where the DHT11 sesnsor data will be stored. These can be scaled by 10 so it can be stored as an int.
  • Finally, when the master request is received, the holdingRegisters[0] and holdingRegisters[1] are sent to the PLC.

Simple enough, right? Well, it should be, but as with all things, stuff happens, and datatypes get mismatched, or weird COM port erros arise. In that event, here is how you troubleshoot it, and what you should see on the screen if you are sending a simple "Hello" to Radzio. 

		#include <ModbusRTUSlave.h>

		#define RS485_DE_RE 5
		#define RXD2 16
		#define TXD2 17

		// 3 holding registers to fit "he" "ll" "o "
		uint16_t holdingRegisters[3] = {26725, 27756, 28448};

		ModbusRTUSlave modbus(Serial2, RS485_DE_RE);

		void setup() {
		  Serial.begin(9600);

		  Serial2.begin(9600, SERIAL_8N1, RXD2, TXD2);

		  // Link all 3 registers and start listening as Slave ID 1
		  modbus.configureHoldingRegisters(holdingRegisters, 3);
		  modbus.begin(1, 9600);

		  Serial.println("Modbus Broadcasting 'Hello '");
		}

		void loop() {
		  // Continuously listen for Modbus requests and serve the array
		  modbus.poll();
		}

Connecting the RTU to OpenPLC

I mentioned earlier that this project was built on the tutorial created by the OpenPLC team. Not much change actually had to be done to the ladder logic, but if a particular process did need to calculate or compute something with the received RTU data, it would be done on an existing or new rung.

The received data does need to store it, and this can be done by assigning variables within the ladder logic diagram. These are called Holding Registers - Read (%IW100). Essentially, we are storing them in memory of the PLC when reading from an RTU. Since they are the datatype of int, it is a good idea at this point to send int data.

An important distinction I might add is that the %IW registers that are read only from a physical pin, and physically different from others, such as Digital In, Digital Out, Analog In, etc.

  • The Prefix (Location):
    • %I - Input: This is Read-only data from a physical pin, analog sensor, or network poll.
    • %Q - Output: Writeable data that is sent to a physical relay, LED, or client device.
    • %M - Memory: Internal scratchpad memory used only within the ladder logic.
  • The Suffix (Size):
    • X - Bit: Boolean, e.g. 1 or 0, or a push button.
    • B - Byte: 8 bits.
    • W - Word: 16 bits. e.g., a standard Modbus Holding Register.
    • D - Double Word: 32 bits. e.g., floating-point math.
I personally found it confusing jumping back and forth between different registers and GPIO pins, and found it easier to keep track with laminated paper and whiteboard markers, especially when tracking down which register needed to be assigned within the actual ladder logic diagram, and when they are remapped.

Summary of Project and Insights

In the beginning of my post, I said this project started with a simple question. As is often the case, the processes that happen in the background are much more complex than we originally assume them to be. This project surprised me on a couple of fronts. The reason why many industrial sites opt to use RS485 is its ruggedized nature and distance capabilities. Under optimal conditions, you can achieve up to 1200 meters of twisted pair communication, and that's entirely without relying on TCP/IP.

This exercise proved to be incredibly valuable in understanding the internal workings of a PLC, at least from the perspective of simple memory operations. From a security standpoint, because the read-only input registers can only be updated by a physical connection (or local logic), they aren't actually modifiable by external Modbus network operations in the same way that an output coil like %QX0.2 might be. Of course, this baseline configuration is far from secure, but it perfectly demonstrates the critical difference between processes that can be interacted with remotely and those that cannot. At least, not through Modbus directly!
